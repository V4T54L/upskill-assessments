# approaches

One document per step, written **before** its code, named for the step it belongs to
(`00-choose-the-problem.md`).

An approach doc is an argument, not a plan. It states what will be built, what was considered
and rejected, and — most importantly — **what would have to be true for this to be the wrong
choice**. A design with no stated failure condition has not been thought about; it has been
described.

Do not revise an approach doc silently after the code disagrees with it. Append a dated note
saying what the code taught you. The gap between the design and what actually got built is the
most useful thing in this directory.
